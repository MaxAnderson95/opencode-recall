# OpenCode session schema and plugin API surface

Resolves research ticket #3. Facts below were read from the OpenCode source at tag `v2.0.5` (commit `79169fe96`, the version Max runs: `opencode2 --version` prints `opencode v2.0.5`) checked out at `~/.btca/agent/sandbox/opencode-v2.0.5`, from Max's live database `~/.local/share/opencode/opencode.db` (read-only, 2026-09-16), and from the current plugin at `~/my-opencode-setup/plugins/recall`. Source paths are relative to `packages/` in the OpenCode repo unless stated. The `dev` branch (commit `88c6c7abc`, 114 commits past v2.0.5) diverges in the schema package layout, so anything here should be re-checked against the release actually targeted when the plugin is built.

## Summary

- A v2 session is one row in `session_v2`; its transcript is a sequence of rows in `session_message`, each a self-contained JSON document (`data` column) discriminated by `type`. There is no `part` table in v2. Assistant text, reasoning and tool calls are an inline `content` array inside the assistant message. The legacy `session`, `message`, `part` tables still exist in Max's file but stopped receiving writes on 2026-08-25.
- Eleven message types exist: `agent-switched`, `model-switched`, `location-switched`, `user`, `synthetic`, `system`, `skill`, `shell`, `assistant`, `compaction`, `idle`. Compaction is its own message, not a flag on an assistant message.
- Child (subagent) sessions link through `session_v2.parent_id` / `Session.Info.parentID`; the parent side records `metadata.sessionID` on the completed `subagent` tool item. Forks link through `fork_session_id` and `fork_boundary`.
- User file attachments are stored inline as base64 in the message JSON (a single screenshot message in Max's database is 1.43 MB), so a snapshot format must decide explicitly whether to carry attachment bytes.
- The public event stream a plugin subscribes to does not include a `session.updated` event (that is V1 only), and `session.idle` is marked deprecated in the schema with no emitter in the v2.0.5 server source. A live capture of `/api/event` on Max's server while two sessions completed turns showed `session.execution.succeeded` for each and zero `session.idle` or `session.status` events. The terminal-turn signals in v2 are `session.execution.succeeded`, `session.execution.failed` and `session.execution.interrupted`. The current plugin listens for `session.idle`, so its event-driven indexing path is dead code on v2.0.5 and only the periodic backfill keeps it current.
- The plugin context cannot list sessions or list a session's messages: `ctx.session` exposes `create`, `get`, `context` (post-compaction messages only), `generate`, `prompt`, `synthetic` and a few controls. Full transcripts must come from the SQLite file, from the HTTP API with the service password, or from the durable event log endpoint.
- Plugins run in-process in a Bun-compiled server binary, one instance per open location, with `ctx.storage` (a namespaced slice of the `kv` table) as the sanctioned durable store and no restriction on `fetch` or timers. Cleanup is the function returned from `setup`.
- Packages install from `github:owner/repo#ref` through npm-package-arg plus Arborist with `ignoreScripts: true`, into `~/.cache/opencode/npm/git-<slug>-<hash>/<generation>/node_modules/<name>`. Startup checks for updates once per 24 h but does not swap the installed package; `opencode plugin update` does.

## Messages

Schema: `schema/src/session-message.ts`. Table: `SessionMessageTable` in `core/src/session/sql.ts`, name `session_message`, columns `id` (text PK, `msg_` prefix, ascending), `session_id` (FK cascade), `type`, `seq` (int, unique per session), `time_created`, `time_updated`, `data` (JSON, the whole message minus `type` and `id`). Order by `seq`, not `time_created`.

Every message shares `Base`: `id`, optional `metadata: Record<string, unknown>`, `time.created` (epoch ms in the encoded JSON). Type distribution in Max's database: assistant 147,221; user 15,562; synthetic 2,915; system 753; idle 383; model-switched 214; compaction 190; agent-switched 86; location-switched 37; `shell` and `skill` have zero rows so far.

### Assistant content items (the v2 replacement for parts)

`AssistantContent` is a tagged union on `type` (`schema/src/session-message.ts:194`). Items have no ids of their own; the current plugin synthesizes `<message_id>#<index>` and that remains the only stable handle.

| Item `type` | Fields | Notes |
| --- | --- | --- |
| `text` | `text`, `state?: ProviderState` | |
| `reasoning` | `text`, `state?: ProviderState`, `time?.{created,completed?}` | Anthropic stores an encrypted `state.signature`; `text` can be empty |
| `tool` | `id` (provider call id), `name`, `executed?`, `providerState?`, `providerResultState?`, `state: ToolState`, `time.{created,ran?,completed?}` | |

`ToolState` (`schema/src/session-message.ts:125`): `streaming {input: string}`, `running {input: Record, metadata: Record}`, `completed {input, content: NonEmptyArray<Tool.Content>, metadata?}`, `error {input, error: SessionError.Error, content?, metadata?}`. `Tool.Content` (`schema/src/tool.ts`) is `{type:"text", text}` or `{type:"file", uri, mime, name?}`; there is no `output` string or `title` string on the state, which the v1 shape had.

Subagent linkage from the parent side: the `subagent` tool sets `metadata: { sessionID, status }` on its completed state and its text content wraps the child output in `<subagent sessionID="..." state="completed">` (`core/src/tool/plugin/subagent.ts:262-264`). The child session row carries `parent_id` pointing back.

### File attachments

`Prompt.FileAttachment` (`schema/src/prompt.ts`) is `{data: Base64, mime, source: {type:"inline"} | {type:"uri", uri}, name?, description?, mention?}`. The base64 payload is persisted in `session_message.data`: the three newest user messages with files in Max's database are 1,427,995 to 1,429,945 bytes each, of which 1,427,456 bytes is `files[0].data`. A hub snapshot that copies message JSON verbatim inherits this; the `sanitize` query flag on the export endpoint exists for this reason (`protocol/src/groups/session.ts:259`).

## Other storage tables

Confirmed by `sqlite_master` in the live file. Relevant to recall:

- `session_v2`, `session_message`: described above.
- `session`, `message`, `part`: V1 tables. `part.data` holds the v1 part JSON (`{type:"text"|"reasoning"|"tool"|...}`), `message.data` holds `{role, ...}`. Last `message.time_created` is 1788008244499 (2026-08-25); 3,569 sessions, 129,897 messages, 568,952 parts. V2 has 4,400 sessions, so about 830 sessions exist only in v2 and any v1-only session is one the migration could not carry.
- `event`, `event_sequence`: the durable per-session event log (`aggregate_id` = session id, `seq`, `type`, `data`, `created`). `session_message` is a projection of this log (`core/src/session/projector.ts`, `message-updater.ts`). 120,001 rows in the live file. Exposed as SSE at `GET /api/experimental/session/:id/log?after=<seq>&follow=` (`protocol/src/groups/session.ts:723`), which is a ready-made incremental sync cursor.
- `session_inbox`, `session_pending`: queued prompts not yet admitted; not transcript.
- `instruction_entry`, `instruction_blob`, `instruction_state`: per-session instruction (AGENTS.md etc.) state.
- `kv`: `key` text PK, `value` JSON, `time_created`, `time_updated` (`core/src/kv/sql.ts`). This backs `ctx.storage`; keys are `plugin:<hex-encoded plugin id>:<key>` (`core/src/plugin/host.ts:583`). Another plugin (`ultra`) already stores per-session keys there.
- `project`, `project_directory`, `workspace`, `worktree`, `permission`, `todo`, `session_share`, `credential`, `account*`: not needed for recall.

## Plugin API surface (Promise flavor, `@opencode/plugin`)

Definition: `Plugin.define({ id, setup(ctx) })` where `setup` may return a cleanup function that OpenCode awaits on unload or replacement (`plugin/src/promise/plugin.ts`, `plugin/src/README.md`). The context is built in `plugin/src/promise/adapter.ts:290-600`. Domains on `ctx`: `app` (`name`, `version`, `channel`), `location` (`Location.Info` of the instance), `options` (this plugin's `options` object from config), `agent`, `aisdk`, `command`, `event`, `experimental.terminal`, `integration`, `mcp`, `model`, `generate`, `permission`, `plugin.list`, `provider`, `reference`, `rpc`, `session`, `shell`, `skill`, `storage`, `tool`, `vcs`, `websearch`, `worktree`.

### Events

`ctx.event.subscribe({signal?})` returns an `AsyncIterable` of `OpenCodeEvent` (`protocol/src/groups/event.ts`), the union of `EventManifest.ServerDefinitions` (`schema/src/event-manifest.ts:74`) plus `rpc.*` and `server.connected`. Each event is `{id, type, data, location?, metadata?}`. The endpoint is documented as volatile: a slow consumer overflows and fails the stream, and events during disconnection are lost.

Session events in the public stream (`schema/src/session-event.ts:643`, all carry `data.sessionID`):

- Lifecycle: `session.created` (projectID, location, parentID?, slug, title?, agent?, model?, metadata?, version), `session.renamed` (title), `session.moved`, `session.permissions`, `session.viewed`, `session.deleted`, `session.forked` (parentID, boundary), `session.agent.selected`, `session.model.selected`, `session.usage.updated`.
- Turn boundaries: `session.execution.started`, `session.execution.succeeded`, `session.execution.failed` (error), `session.execution.interrupted` (reason: user, shutdown, superseded, inactivity). These drive `time_idle` and the `idle` message.
- Streaming detail: `session.step.*`, `session.text.*`, `session.reasoning.*`, `session.tool.{input.*,called,progress,success,failed}`, `session.compaction.{started,delta,ended,failed}`, `session.shell.*`, `session.skill.activated`, `session.synthetic`, `session.inbox.*`, `session.instructions.updated`, `session.retry.scheduled`, `session.revert.*`.
- Also in the manifest: `session.status` (`data.status.type` idle, busy, retry) and `session.idle` (`data.sessionID`) from `schema/src/session-status-event.ts`, where `Idle` carries a `// deprecated` comment. `rg` over `packages/core` and `packages/server` at v2.0.5 finds no code that publishes either; the desktop client derives running state from `session.execution.*` (`client/src/solid/data.ts:1008-1040`). Runtime confirmation on 2026-09-17: a 75 second `curl -N` capture of `GET /api/event` on the v2.0.5 server hosting this research session (Basic auth with the server password) recorded two sessions finishing a turn (`ses_f52e6db74ffejCjqmTyh5lAPvV` and `ses_f531f3d62ffeoVc8spo2Hk6bdy`); each produced `session.execution.started` and `session.execution.succeeded` (with `durable.seq`), and the stream contained no `session.idle` or `session.status` event at all. Build on `session.execution.{succeeded,failed,interrupted}`.
- Servers are per client: Max's machine had three `opencode serve` processes (the registered `--service` one on 49374 plus two started by T3 Code on 54968 and 56331, each with its own `OPENCODE_SERVER_PASSWORD`). A plugin only sees events from the server that loaded it, so an uploader must be installed in whichever configuration every server reads (the global `~/.config/opencode/opencode.jsonc`), and it cannot assume one process owns all sessions.
- Not in the stream: `session.updated` exists only in the V1 schema (`schema/src/v1/session.ts:581`); `session.compacted` is defined but excluded from `ServerDefinitions`.

### Tools

`ctx.tool.transform((editor) => editor.add({name, description, input, output?, options?, execute}))` (`plugin/src/promise/tool.ts`). `input` accepts an Effect `Schema`, a Standard Schema, or raw JSON Schema (`Tool.ValueSchema`, `schema/src/tool.ts:44`); with raw JSON Schema `execute` receives `unknown`. `execute(input, ctx)` gets `{sessionID, agent, messageID, id, progress(metadata)}` and returns `{output?, content?: string | Content[], metadata?}`. `options: {codemode: false}` keeps the tool out of Code Mode; `options.namespace` groups tools. `ctx.tool.hook("execute.before" | "execute.after")` intercepts every tool call, including other plugins' tools. `editor.update`, `editor.remove`, `editor.list`, `editor.get` edit existing tools.

### Prompt and instruction injection

- `ctx.session.hook("context", (event) => ...)`: mutable `event.system: SystemPart[]`, `event.messages`, `event.tools`, `event.options` immediately before each agent-loop model call; changes are per request and not persisted (`plugin/src/promise/session.ts:26-40`, docs `services/www/src/docs/content/build/plugins/index.mdx:1300`). Separate hooks `compaction`, `generate`, `title` cover the auxiliary requests; `kind` on `model.request` / `http.request` tells them apart.
- `ctx.session.hook("prompt", ...)`: rewrite the user prompt once at admission (text, files, agents, skills, metadata, delivery).
- `ctx.session.synthetic({sessionID, text, resume?})`: persist a synthetic message into the transcript. The built-in plan plugin combines `context` and `synthetic` to keep a reminder in place across compaction (`core/src/plugin/plan.ts`).
- `ctx.agent.transform((draft) => draft.update(id, agent => { agent.system = ...; agent.hidden = true; agent.permissions.push(...) }))`: define or reshape an agent, which is how the current plugin builds its tool-less summarizer agent.
- There is no direct "append to the global system prompt" call; `context` on every kind is the equivalent.

### Config access

`ctx.options` is the only config the plugin receives: the `options` object from the `{package, options}` form of a `plugins` entry (`schema/src/config/plugin.ts`, `core/src/config/plugin/source.ts:114`). There is no `ctx.config` domain in the Promise context (`plugin/src/promise/plugin.ts:26-52`). The current plugin reads its own `~/.config/opencode/recall.json` and polls its mtime; that remains necessary if per-host settings should live outside `opencode.jsonc`.

### Sessions and the worker model

`ctx.session` is `Pick<SessionApi, "create" | "get" | "switchAgent" | "switchModel" | "prompt" | "generate" | "command" | "synthetic" | "interrupt" | "update" | "move" | "wait" | "context"> & { hook }` (`plugin/src/promise/session.ts:145`). Missing from the pick, though present on the HTTP client: `list`, `remove`, `export`, `import`, `message.get`, and the separate `message.list` domain (`client/src/promise/generated/client.ts:487-1060`).

- `ctx.session.create({title?, agent?, model?, location?, metadata?, permissions?, id?})` and `ctx.session.generate({sessionID, prompt})` returning `{text}` are what the current summarizer uses (`lib/summarize.ts:42-50`); both still exist. `generate` "generates transient text from the current session context without mutating session history" (`protocol/src/groups/session.ts:717`).
- `ctx.generate.text({model: {providerID, id}, prompt})` (`/api/experimental/generate`) generates with a chosen model and no session at all (`plugin/src/promise/adapter.ts:338`, docs line 712). This removes the need for the persistent hidden worker session and the `summary_worker:<tag>` id the current plugin keeps in its sidecar; whether it honors an agent system prompt is not established, so the tool-less worker agent would need to be replaced by prompt text.
- `ctx.session.context({sessionID})` returns `PublicSessionMessage[]` for messages after the last compaction only (`protocol/src/groups/session.ts:566-575`).
- `ctx.model.list()` returns the active model catalog; the current plugin already uses it to validate `providerID/modelID/variant`.

### Reading full transcripts

Three routes exist; none is the plugin context itself.

1. Open `~/.local/share/opencode/opencode.db` read-only with `bun:sqlite` and read `session_v2` / `session_message` (what `lib/source.ts` does today). The path is `Global.Path.data` (`util/src/global.ts`), XDG-derived. Works only on the host that owns the database, which is the case for the uploader.
2. Call the HTTP API on the local service: `GET /api/session/:id/message?limit&order&cursor&type` (`protocol/src/groups/message.ts`, 200 per page, cursor pagination) or `GET /api/experimental/session/:id/export?sanitize=` returning `{info, messages}` (`protocol/src/groups/session.ts:257`). Authentication is HTTP Basic, username `opencode`, password from `~/.local/state/opencode/service.json` (`server/src/auth.ts:17`, `client/src/service.ts:45`). A plugin can reach this with `fetch` but must locate and read the registration file itself.
3. Follow `GET /api/experimental/session/:id/log?after=<seq>&follow=true` for durable events and rebuild messages, which is how the server itself builds `session_message`.

### Storage and background work

- `ctx.storage.get/set/remove/scan({prefix, after?, limit?})` stores JSON under `plugin:<id>:` in the `kv` table (`core/src/plugin/host.ts:583`, `plugin/src/storage.ts`). It is per plugin id, shared by every location instance, and lives inside `opencode.db`, so it is in Max's existing encrypted backup. It is a key-value store, not a place for FTS or vectors.
- The server is a Bun single-file executable (`cli/script/build.ts:134`, `compile` target `bun`), plugins are `import()`ed into that process (`util/src/runtime/import.bun.ts`, `plugin/src/host.ts`), so `bun:sqlite`, `Bun.sleep`, `Bun.spawn`, `fetch`, `setInterval` and worker processes are all available and unrestricted. Nothing in `core/src/plugin/host.ts` sandboxes network or filesystem access.
- The plugin supervisor is a location node (`core/src/plugin/supervisor.ts:179`, `makeLocationNode`), so one `setup` runs per open location and `ctx.location` names it (docs line 77: "This is the plugin instance's location, not the location of every session it can access or event it receives"). Every instance receives every location's events. An uploader must therefore either dedupe across instances (a lease in `ctx.storage` or SQLite, as `BackfillLease` does today) or elect one instance.
- Config edits under watched directories reload plugins: the supervisor recomputes generations and the old instance's cleanup runs (`core/src/plugin/supervisor.ts`, docs `plugins.mdx` "Reload"). Long-running work must be cancellable from the cleanup function; the current plugin drains a `pending` set with an 8 s cap.
- Plugin load failures are isolated: a failing generation is logged with an `err_` ref and the previous generation keeps running (`core/src/plugin/supervisor.ts:64-80`).

## Installing and updating from GitHub

- Config: `"plugins": ["github:MaxAnderson95/my-opencode-setup#plugin-recall"]` or `{ "package": "github:...#ref", "options": {...} }` (`schema/src/config/plugin.ts`). Any `npm-package-arg` git spec is accepted: `github:` shortcut, `git+ssh://`, branch, tag, full commit, and `::path:sub/dir` (`util/src/npm.ts:59-83`, docs `plugins.mdx:96-107`). Max's skill notes record that `::path:` installed the repository root on beta-19425, which is why each plugin is published to its own branch.
- Install: `Npm.add` resolves the spec with `npm-package-arg`, writes a `package.json` with a single dependency, and runs `@npmcli/arborist.reify` with `ignoreScripts: true`, `binLinks: true`, `savePrefix: ""` into a staging dir, then renames it to `~/.cache/opencode/npm/git-<repo-slug>-<12 hex of sha256(spec)>/<epoch ms generation>/` (`util/src/npm.ts:132-320`). The two newest generations are kept (`collect`). Confirmed on disk: `~/.cache/opencode/npm/git-my-opencode-setup-019db60f380b/1789565456414/package.json` depends on `oc-plugin-recall: github:MaxAnderson95/my-opencode-setup#plugin-recall`.
- Because lifecycle scripts never run, the package must be loadable as shipped: TypeScript source is fine under Bun, but nothing will be compiled.
- Entrypoint resolution: `./server` export, then root export or `main`, then `index`; `./tui` and `./rpc` are optional extra entrypoints (`plugin/src/host.ts:16-43`).
- Update: at startup the server loads the cached generation, installs anything missing in the background, and runs `PluginUpdate.check` at most once per 24 h per target without changing the installed package (`core/src/plugin/update.ts:9,36-49`, docs `plugins.mdx:111-114`). `opencode plugin check` reports, `opencode plugin update [target]` calls `plugin.update` on the server for server plugins, which runs `Npm.update` with `preferOnline` and `noGitRevCache` (`cli/src/commands/handlers/plugin/update.ts`, `util/src/npm.ts:192`). Exact npm versions and full commit hashes are treated as pinned and skipped.
- Peer dependency: the current package pins `"@opencode/plugin": "2.0.4"` while the server is 2.0.5 (`package.json` at `plugins/recall`); `@opencode/plugin` exports `.` (Promise), `./effect`, `./host`, `./tui` (`plugin/package.json`).

## Differences from what the current plugin assumes

The current plugin (`recall.ts`, `lib/source.ts`, `lib/schema.ts`, `lib/summarize.ts`) already targets the v2 tables and the v2 Promise API, so most of it holds. The gaps:

1. **Turn-complete signal.** `recall.ts:312` indexes on `event.type === "session.idle"`. That event is deprecated in `schema/src/session-status-event.ts`, no emitter exists in the v2.0.5 server, and the live capture confirmed it never fires; the plugin's periodic backfill has been doing all the work. The new plugin should trigger on `session.execution.succeeded` / `failed` / `interrupted` (excluding `reason: "shutdown"`, matching `projectIdle`), and can additionally use `session.renamed`, `session.moved`, `session.deleted` and `session.forked` to keep hub metadata current.
2. **No `session.updated`.** Title, directory and metadata changes arrive as separate `session.renamed`, `session.moved`, `session.permissions` events, or by re-reading `session_v2.time_updated`.
3. **Normalized shape is v1-flavored.** `source.ts` flattens v2 into `{type:"tool", tool, state:{status,title,output}}`, inventing `title` from input values and `output` from text content (`toolTitle`, `toolOutput`). The hub archive should model the v2 shape directly: `tool.name`, `state.input`, `state.content[]`, `state.metadata`, `state.error`, so subagent `metadata.sessionID`, file content items and error states are not lost.
4. **Message types dropped.** `V2_TYPES` skips `system`, `idle`, `agent-switched`, `model-switched`, `location-switched`. `system` carries Code Mode catalog text (753 rows) and `idle` is the authoritative turn boundary with outcome; both are useful to the archive even if not indexed for search.
5. **Assistant attribution.** `source.ts` ignores `agent`, `model`, `cost`, `tokens`, `finish`, `error`, `retry` and `snapshot` on assistant messages; `session.agent`, `session.model`, `parent_id` and `metadata` beyond `parent_id`; and never reads `fork_session_id`. The hub model should carry these.
6. **Attachments.** The plugin never touches `files`, so it never faced the base64 payload. A snapshot copying message JSON must strip or externalize `files[].data` or accept multi-megabyte uploads.
7. **Compaction boundary.** `compactionBoundary` uses `max(time_created)` of completed compactions; `seq` is the correct ordering key, and `session.context` gives the server's own notion of the live window.
8. **Worker sessions.** The summarizer creates a persistent hidden session per model tag and stores its id in the sidecar (`summarize.ts:84-112`). `ctx.generate.text` is a session-free alternative; if the hub runs summaries server-side instead, the plugin needs neither. The `ctx.session` pick still lacks `remove`, so orphaned worker sessions cannot be deleted from a plugin.
9. **Durable state location.** The sidecar `index.db` under `~/.local/share/opencode-recall` is outside OpenCode's knowledge. `ctx.storage` now exists for small per-host state (last uploaded `seq` per session, hub cursor, lease), backed by `kv` in `opencode.db` and covered by Max's backup script.
10. **Multi-instance assumption.** `BackfillLease` comments say "every opencode process loads its own copy"; in v2 it is one process with one instance per location, and every instance sees every event. The dedupe requirement is the same, the reason differs.
11. **Config source.** Nothing in `recall.json` can move into `ctx.options` without moving it into `opencode.jsonc`; the plugin's mtime-polling reload of `recall.json` is still the only way to hot-reload out-of-band settings.
12. **Peer version.** `@opencode/plugin` peer is pinned at `2.0.4` while the runtime is `2.0.5`; the hub plugin should pin to the tested runtime and re-verify the `Pick` in `plugin/src/promise/session.ts` on each bump, since that list changed the API surface without a schema change.
